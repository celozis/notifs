# Перенос согласованного дизайна в WPF

19 ноября 2026 пользователь подтвердил Q1–Q46, назначил дополненный графитово-янтарный прототип целью Windows-приложения и согласовал разбиение на 19 рабочих тикетов. Подробные постановки опубликованы в GitHub: существующие #1–#10 обновлены, #11–#20 добавлены. [#1](https://github.com/celozis/notifs/issues/1) — общий спек и карта покрытия всех решений интервью; ниже навигация по работам, а не второе определение поведения.

Поведение — в [продуктовой спецификации](design-spec-2026-11-18.md), оформление — в [Master](../../design-system/notifs/MASTER.md) и точных токенах. Основное WPF-приложение ещё требует реализации этих постановок. Публикация тикета не означает завершение функции.

## Перед началом тикета

1. Проверить реальные блокеры и прочитать полное тело/комментарии тикета через gh. Взять работу, все блокеры которой завершены; родитель #1 сам не является блокером. На момент публикации первым доступен #2.
2. Прочитать AGENTS.md, продуктовую спецификацию, Master и [README эталона](../../design-system/notifs/reference/README.md). В рабочей ветке должен присутствовать комплект из коммита `f0462998e790e7fd9b4efce4ed8e0a4722875b71`, опубликованного в `codex/design-handoff`.
3. Открыть [автономный notifs-reference.html](../../prototypes/ui-concepts/notifs-reference.html) из клона браузером, выполнить относящийся к задаче путь и посмотреть PNG состояний, перечисленных в тикете. Если браузер недоступен, открыть PNG средствами просмотра изображений; чтение HTML не заменяет визуальную проверку.
4. Реализовать полный пользовательский путь: прикладные команды, миграцию/SQLite, WPF-представление и проверку. Сохранить существующие данные. JavaScript демонстрации не переносить в продукт; время/источники/хранение отделены от представления.
5. Проверить собственные сценарии с реальным временным хранилищем/управляемыми часами и через рабочее окно, повторное открытие базы, ошибки без потери ввода. Нативные обещания проверять настоящими окнами/системными событиями.
6. Сопоставить WPF и соответствующий эталон при одинаковых логических размере/DPI, данных и времени. Сравнивать содержимое без внешних полей и декоративной рамки HTML. Палитра, геометрия, типографика, состояния, переносы и доступность входят в готовность каждого тикета.
7. Приложить к итоговому отчёту снимки реализации и результаты по критериям, назвать непроведённые проверки. Отсутствующий UI/заглушка/непроверенная нативная доставка не засчитываются как готовая функция.

## Эталон и исходники демонстрации

Тикеты закрепляют ссылки за исходным коммитом эталона `f0462998e790e7fd9b4efce4ed8e0a4722875b71`; это позволяет другим чатам открыть те же материалы. Позднейшие обновления статуса документации не меняют содержимое прототипа/PNG. Старые пометки ожидания визуальной оценки в исходном комплекте описывают стадию до текущего запроса пользователя.

Для исправлений самого эталона использовать [источник дополнений JS](../../prototypes/ui-concepts/workspace-additions.js), [CSS](../../prototypes/ui-concepts/workspace-additions.css) и [builder](../../prototypes/ui-concepts/build_reference.py), затем штатную проверку/фиксацию снимков, описанную в README эталона. Автономный HTML/inline HTML генерируются, Lucide — локальная зависимость с лицензией. Их не читать целиком для поиска логики и не редактировать вручную. При реализации WPF визуальное направление сохраняется; нового выбора темы нет.

Кнопки продвижения времени, сна, перезапуска и сброса под макетом — инструменты демонстрации. Они не входят в интерфейс настоящего приложения. Фон, мониторы, автозапуск, планировщик и SQLite требуют настоящей реализации и проверки, даже если демонстрация визуально похожа на готовый продукт.
